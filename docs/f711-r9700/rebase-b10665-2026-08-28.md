## Zhrnutie

Produkčná vetva `f711-rdna-b10488-chatfix` je rebasovaná na upstream **b10665**
ako `f711-rdna-b10665-chatfix`. Medzi ramenami je **177 upstream commitov**, nie

Odpoveď: **nestojí**. PPL identická na oboch modeloch, vision 3/3 na oboch

**Nasadené** od 28. 8. 2026 ako default `serve-claude-code-qwen38.ps1`.

## Čo sa v stacku zmenilo

Z 28 commitov nášho stacku prežilo 25. Vypadli tri:

| commit | dôvod |
|---|---|
| `chat: scope qwen3-coder workarounds (#27679)` | už upstream (`0cc5b1495`) |
| `spec: avoid binding reference to null pointer (#27404)` | už upstream (`f466cfa38`) |
| `llama: align attn_gate TP split granularity with attn_q` | prekonaný upstreamom |

Ten tretí stojí za vysvetlenie: upstream medzitým pridal do
`get_split_granularity` vlastnú vetvu pre `pattern_attn_gate_weight`, ktorá gate
tenzoru dá `granularity_head`/`granularity_q`. Náš fix riešil presne to isté
(gate dostával granularitu 1 a rozdelil sa inak než attention, ktorú kŕmi), takže
by len duplikoval upstream. Týka sa to aj tak len multi-GPU tensor parallelu, kde
my nebežíme.

Náš zvyšný stack sa tým zmenšil o dva lokálne patche — `#27679` sme cherry-pickli
26. 8. a odvtedy bol jediným dôvodom, prečo si vetvu držať aktuálnu ručne.

## Konflikty

Tri, z toho dva triviálne (`tests/test-backend-ops.cpp`: raz pridanie
`GGML_TYPE_BF16` do filtra vedľa upstreamového `v_is_view_of_k` pre DeepSeek MLA,
raz únia dvoch nezávislých blokov perf test-caseov).

Vecný bol jeden: **`ggml/src/ggml-cuda/rope.cu`, 6 hunkov**. Upstream pridal do
rope kernelov `n_offs`/`inplace` (`ggml_rope_set_offset`), my na `rope_multi`
nesieme `D`-cast výstupu a ROPE+VIEW+SET_ROWS fúziu. Obe zmeny sa dotýkajú tých
istých riadkov — signatúry, early-return vetvy a zápisu výsledku.

Riešené ako únia oboch podľa vzoru `rope_neox` **v tom istom súbore**, ktorý sa
zmergoval automaticky a obe vlastnosti už nesie:

```
template <bool forward, bool has_ff, typename T, typename D>
static __global__ void rope_multi(..., const int n_dims, const int n_offs, ...,
                                  const int64_t * row_indices,
                                  const int       set_rows_stride,
                                  const bool      inplace) {
    ...
    if (i0 < n_offs || i0 >= n_offs + n_dims) {
        if (inplace) { return; }
        dst[idst + i0/2 + 0] = ggml_cuda_cast<D>(x[ix + i0/2 + 0]);
        ...
    }
    dst[idst + n_offs/2 + 0] = ggml_cuda_cast<D>(x0*cos_theta - x1*sin_theta);
```

Kontrola, že sa pri 177 commitoch nič ticho nestratilo: diffstat novej vetvy voči
`b10665` je identický so starou vetvou voči `b10488` vo všetkých 20 spoločných
súboroch. Rozdiel sú len tri zámerne vypustené súbory a `rope.cu` 74 → 72 riadkov
z tohto mergu.

Po úlohách (build, b10488 → b10665): `blazor-bind` 3/3 → 2/3, `wpf-mvvm`
3/3 → 2/3, `efcore-query` 1/3 → **2/3**, ostatné bez zmeny. Rozdiely idú **oboma

`build_ok` sa čítať nedá. Silnejším dôkazom neutrality je identická PPL na oboch
modeloch; táto sada je kontrola, že sa nestalo niečo hrubé — a nestalo.

## CI: pribalenie HIP runtime (#26973) NEPOMÁHA

Upstream v tomto okne pridal do `windows-rocm` release jobu krok, ktorý vedľa
binárok kopíruje `amdhip64_7.dll`, `rocm_kpack.dll` a `amd_comgr.dll` (issue
#26929 — driverová kópia v System32 vyhráva loader search). Portoval som ho do
`f711-rocm.yml` s očakávaním, že tým odpadne `patch-rocm-runtime.ps1`.

**Neodpadol.** Artefaktu chýba niečo iné: `rocblas.dll`, `hipblas.dll`,
`rocsolver.dll`, `libhipblaslt.dll` a Tensile kernel adresáre `rocblas\library\`
+ `hipblaslt\library\gfx1201\`. Overené na b10665: `--list-devices` hlásil
`(none)` s pribalenými DLL aj po ich odsunutí bokom, a kartu našiel až po
`patch-rocm-runtime.ps1`.

Krok je preto **revertnutý** (`86d4a140a`). Zip kvôli nemu rástol o ~140 MB a
runtime aj tak berieme z jedného referenčného stromu (`b10400`), aby bol rocBLAS
naprieč ramenami konštantný.

## Poznámky k metodike

- Speed beh na pozadí s 10-minútovým limitom bol po štyroch iteráciách zabitý;
  dobehnutý cez `-Schedule` + `-VisitStart`. Zabitý wrapper nezanechal bežiaci
  `llama-server`, ale spoľahnúť sa na to nedá — kontrolovať treba vždy.
- `-Schedule` sa cez `Start-Process -File` odovzdať **nedá**: pole sa buď zlepí
  do jedného prvku s čiarkami, alebo sa zvyšné tokeny naviažu pozične na ďalší
  parameter (`$NewBin`). Rovnaký vzor ako pri dispatcher skriptoch. Riešenie je
  wrapper skript, ktorý harness volá s `@(...)`.
